Regression Testing

Rerun old checks after a change so yesterday's features still work tomorrow.

Core concept

What Is Regression Testing?

Regression means...

  • A feature goes backwards after a change
  • Something that passed before now fails
  • The break may be far from the edited code
  • Users see it as an update making the product worse

Testing means...

  • Rerun useful previous checks
  • Compare new results with the baseline
  • Focus on critical journeys first
  • Keep evidence of pass, fail, and retest
change made -> old checks rerun -> unexpected failures investigated -> release decision
Timing: 5 minutes. Break down the word regression and emphasise that not every retest is a full retest of everything.

When Should You Run It?

After a bug fix

The fix may change shared logic, validation, or data handling.

After a new feature

New behaviour can collide with existing workflows.

After refactoring

The product should behave the same even if the code was tidied.

Before release

Use the pack as a final confidence check before users receive it.

Rule of thumb: the closer you are to release, the more carefully you choose and record regression checks.

Timing: 4 minutes. Ask learners which event deserves a smoke pack only and which deserves a wider regression pack.
Interactive: flip cards

Smoke vs Regression vs Full Suite

Smoke

Fast checks that the build is not obviously broken. Example: login, open dashboard, create a basic order.

Regression

Selected old checks based on what the change might affect. More focused than everything, deeper than smoke.

Full suite

All planned tests. Useful before major releases, but often too slow after every small edit.

Timing: 5 minutes. Let learners flip the cards, then ask them to rank the three by speed and confidence.

Reading the Results

1. Compare

What passed in the baseline but fails now?

2. Triage

Is the failure a product bug, data issue, or brittle test?

3. Investigate

Link failures to changed files, shared logic, and risk areas.

4. Retest

Fix the new bug and rerun the affected checks.

Baseline matters

A regression result only makes sense if you know what the expected passing behaviour looked like before the change.

Timing: 5 minutes. Use the suite runner output and ask learners to separate new regression failures from tests that were already failing.

Risk-Based Selection

Changed area

  • Files or screens edited
  • Business rules touched
  • Data fields changed
  • Third-party services touched

Nearby risks

  • Shared helpers
  • Critical journeys
  • Previous bug clusters
  • High-use features

Pack choice

  • Smoke first
  • Add targeted regression
  • Automate repeatable checks
  • Escalate to full suite when risk is high

Case Study: Fixed Checkout, Broke Login

Classroom scenario E-commerce demo app One-line helper change

The story

A team fixed checkout totals by changing a shared getCurrentUser() helper. The checkout test passed, but returning users were logged out when moving from basket to payment.

The lesson

The edited code looked like "checkout", but the shared helper also powered login sessions. A small regression pack would have caught it before release.

Real-world echo: incidents such as Knight Capital show how untested changes and deployment gaps can become expensive very quickly. At classroom level, the lesson is simple: old behaviour needs protection when code changes.

Timing: 8 minutes. Walk through the scenario and keep the Knight Capital reference high level: avoid finance detail, focus on change control and regression safety.

Common Regression Testing Faults

Symptom Likely cause Fix
Missed regression in a critical journey Pack only covered the changed screen Map shared code and critical paths before choosing checks
Tests fail randomly Brittle tests depend on timing, order, or unstable data Stabilise setup data and remove unnecessary waits
No one knows if a fail is new No baseline or previous results saved Record the last known passing run and compare against it
Pack takes too long to run Everything is treated as equally important Split smoke, targeted regression, and full-suite layers
Bug fix retested but neighbours ignored Risk analysis stopped at the ticket title Review changed files, shared helpers, and user journeys
Automation reports are ignored Failures are noisy or hard to interpret Keep tests meaningful, readable, and linked to user value
Timing: 7 minutes. Use the table as a diagnosis activity: give a symptom and ask learners to predict the likely cause before revealing the fix.

A Practical Regression Workflow

Understand change

Read the bug report, commit, or release note. What behaviour changed?

Choose pack

Start smoke, add high-risk old checks, and note what is out of scope.

Run and record

Capture pass/fail, environment, data, and build/version details.

Act on failures

Raise a clear bug report, retest the fix, and update the pack if needed.

good regression note = change + pack used + result + evidence + next action
Timing: 6 minutes. Stress that a tidy workflow is useful even when tests are manual; automation improves speed, not thinking.

Practical Task: Build and Run a Regression Pack

Brief

  • Read a short bug report for a checkout or login fix
  • Choose a smoke check and 5 targeted regression checks
  • Run the checks on the demo app or provided screenshots
  • Mark pass, fail, blocked, or not run
  • Write one follow-up bug report if a regression is found

Success criteria

  • Pack choices are linked to the change risk
  • Critical user journey is covered first
  • Results include build/version and test data
  • Evidence shows before/after or pass/fail proof
  • Any new failure has clear repro steps

Evidence checklist

Screenshot of results grid, selected regression pack, environment details, failed-step screenshot if relevant, and a short reflection on what you would automate next.

Timing: 10 minutes. Set the practical task and clarify what evidence learners should save for assessment or portfolio review.

Searchable Glossary

Regression testing
Rerunning previous checks after a change to catch accidental breakages.
Regression bug
A fault where something that used to work no longer works after a change.
Smoke test
A small set of fast checks that confirms the build is not obviously broken.
Full suite
All planned tests for a product, often slower but more complete.
Baseline
The known previous result or behaviour used for comparison.
Risk-based testing
Choosing tests based on likelihood and impact of failure.
Critical path
A user journey that must work, such as login, payment, save, or submit.
Test pack
A selected group of checks to run for a purpose, such as smoke or regression.
Brittle test
A test that fails for reasons unrelated to the product behaviour being checked.
False failure
A failed test result caused by test setup or environment rather than a real product bug.
Automation
Using scripts or tools to run repeatable tests more quickly and consistently.
Retest
Running a failed check again after a fix to confirm that specific issue is resolved.
Impact analysis
Thinking through which features, files, data, or users may be affected by a change.
Test evidence
Saved proof of what was tested, what happened, and what build or data was used.

Key Takeaways

Retest after change

A fix is not finished until important old behaviour is still protected.

Use risk to choose

Focus on changed areas, shared code, and critical user journeys.

Keep evidence

Record pack, result, environment, data, and follow-up action.

Automate repeat work

Automation helps the same regression checks run faster and more consistently.
