Load/Stress Concept

Safely explore response time, virtual users, and the breaking point

OCN NI Level 2–3 — Software testing
Timing: 2 minutes. Set the tone immediately: this is a classroom-safe conceptual lab, not permission to attack real sites or school systems.

Learning objectives

By the end of this lesson, you will be able to:

  • Compare load, stress, soak, and spike testing in plain language.
  • Predict how response time and error rate change as virtual users increase.
  • Find a breaking point conceptually using an isolated simulation.
  • Apply authorisation and safe-lab rules before any performance test.
  • Record baseline, ramp steps, evidence, and a careful conclusion.
Timing: 3 minutes. Ask learners which objective feels most technical and which feels most ethical. Emphasise that both matter.

Classroom hook

A school ticket booking site works fine on Monday morning. On ticket-release day, hundreds of users arrive together. What should the team have tested before the rush?

Safety boundary

Never run load tools against real websites, school Wi-Fi, cloud systems, or shared services unless you have written authorisation and a controlled plan.

Timing: 4 minutes. Use the ticket-release scenario as the lesson story. Invite examples of queues: canteen, online shop, games launch, exam results portal.

Load vs stress testing

Load testing

  • Uses expected or agreed peak demand.
  • Checks whether normal service remains usable.
  • Measures latency, throughput, and errors.
  • Answers: "Can we handle Friday lunchtime?"

Stress testing

  • Pushes beyond expected demand in a safe lab.
  • Finds the breaking point and recovery behaviour.
  • Stops before harm spreads to users or systems.
  • Answers: "What fails first, and how gracefully?"
Timing: 5 minutes. Keep the distinction simple: load is expected pressure; stress is beyond normal pressure. Repeat that both need permission.

Response time vs users

What the curve teaches

  • At low traffic, extra users may barely affect response time.
  • Near capacity, small increases cause large delays.
  • After the cliff, errors and timeouts often appear.
  • The goal is to learn safely before real users suffer.
Timing: 5 minutes. Point to the gentle slope and then the cliff. Ask: where would you set an alert before the cliff?

Metrics that tell the story

Latency / response time

How long one request takes from user action to response.

Throughput

How much useful work the system completes per second.

Virtual users

Simulated users following a test script in a controlled environment.

Error rate

The percentage of requests that fail, time out, or return bad responses.

Baseline first

Without a baseline, you cannot prove whether the test made things worse, better, or simply revealed a pre-existing network issue.

Timing: 4 minutes. Link each metric to a user experience. Latency is waiting; throughput is flow; errors are failed tasks.

A safe performance test plan

1

Scope

Target, owner, time window, maximum load, and stop rule.

2

Baseline

Record response time and errors before pressure is added.

3

Ramp

Increase users gradually; do not jump straight to extreme load.

4

Observe

Watch app, server, and network metrics together.

5

Recover

Stop, confirm recovery, save evidence, and report clearly.

Stop rule example

Stop the lab test if error rate reaches 5%, response time exceeds 1 second for two steps, or the teacher says stop.

Timing: 6 minutes. Connect this to test planning from earlier software testing decks. The stop rule is part of being professional.

Case study: ticket-release day

Classroom-safe scenario

A fictional school launches tickets for a robotics showcase. The booking app is fine with 20 visitors, but at 12:30 hundreds of pupils try to reserve seats at once. Pages take 8 seconds, some bookings fail, and the office receives duplicate emails.

What the team should test

  • Expected peak users at ticket release
  • Response time during a controlled ramp
  • Error rate and duplicate booking risk
  • Recovery after the rush

What they must not do

  • Attack a real ticket website for practice
  • Flood the school Wi-Fi to "see what happens"
  • Hide tests from the system owner
  • Ignore signs of user impact
Timing: 6 minutes. Keep this fictional and safe. Ask learners what evidence would help the team fix the booking app.

Common faults and fixes

FaultWhy it is a problemSafer fix
Testing production without permissionMay disrupt real users and breach policy or law.Get written authorisation or use an isolated lab/staging target.
Mistaking network congestion for app failureSlow Wi-Fi can hide whether the application is actually the bottleneck.Capture network and app metrics; compare against baseline.
No baselineYou cannot prove what changed under load.Record idle/light-load response time, errors, CPU, and throughput first.
Jumping straight to extreme stressBreaks the system before useful data is collected.Ramp gradually and pause at each step.
Only measuring average response timeAverages hide the slowest user experiences.Record high percentiles or worst observations as well as averages.
No stop rule or contactThe test may continue after harm begins.Agree stop thresholds and a responsible adult/system owner contact.

Practical task: safe mini test report

Brief

  • Use the simulator or teacher-approved lab target.
  • Run baseline, 3 load steps, and 1 controlled stress step.
  • Stop at the agreed threshold.

Success criteria

  • Correctly label load vs stress.
  • Explain response time trend.
  • Identify the breaking point conceptually.
  • State authorisation and scope.

Evidence checklist

  • Safety checklist screenshot or signed plan.
  • Table of users, latency, errors, throughput.
  • Graph or annotated simulator capture.
  • Short conclusion and next action.

Report sentence starter

"Under expected load, the system stayed usable until __ users. During controlled stress, the first warning sign was __, so the safe operating limit should be below __."

Timing: 8 minutes. This can become the assessed activity. Make evidence concrete: screenshots, table, and conclusion.

Interpreting results carefully

Check the network

If every app is slow, the Wi-Fi or internet link may be the bottleneck.

Check the server

High CPU, memory, or disk activity can explain rising response time.

Check the app

Slow database queries, locks, or inefficient code may appear only under load.

Check the user journey

A login page may pass while checkout or booking fails under pressure.

Timing: 5 minutes. Reinforce that a performance result is evidence, not a guess. Link to performance monitoring tools.

Key Takeaways

Load = expected peak

Check the service is usable under realistic demand.

Stress = safe limit finding

Push beyond normal only in a controlled, authorised lab.

Baseline + metrics

Compare response time, throughput, and errors with evidence.

Authorisation first

Never attack real sites or shared school systems.
