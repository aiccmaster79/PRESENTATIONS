Why Debuggers Matter

A debugger lets you pause a running program, inspect variables, and step line-by-line — faster and clearer than scattering print() everywhere. In industry, this is how developers and testers find logic faults without rewriting the app for every guess.

10×Faster than print-hunting
LiveWatch values as you step

Classroom tip

Reproduce the bug first, then breakpoint just before the suspicious line — don’t step from line 1 of a huge file.

Toolkit

Debugger Toolkit

Click or press Enter/Space to flip each card

Breakpoint

Pause when this line is about to run. Click the gutter for a red dot, or press F9. Run with F5 until you hit it.

Step Over

Run the current line (including a whole function call) without diving inside. Stay at this level of the call stack. Usually F10.

Step Into

Enter a function call to see its body line-by-line. Use when the bug might be inside a helper. Usually F11.

Continue

Resume running until the next breakpoint (or the program ends). Skip the boring middle once you’ve seen what you need.

Watch

Pin expressions or variables (e.g. total, i) and see them update every step. Locals shows scope automatically.

Call Stack

Shows which functions called you here. Jump up the stack to see caller arguments when a nested bug is hard to spot.

Have pairs flip cards and teach each other one tool. Stress Over vs Into with a short demo later. Timing: ~6 min.

Print vs Debugger

Print-debugging

  • Add print() / console.log then re-run
  • Easy for tiny scripts
  • Pollutes code; easy to leave prints in
  • Hard to see many variables at once
  • Timing bugs can disappear when you print

Debugger

  • Pause without rewriting the source
  • Inspect Locals / Watch live
  • Step Over / Into / Continue
  • Call Stack for nested calls
  • Industry-standard for real projects

Rule of thumb: prints for a quick smoke test; debugger when values look wrong and you don’t know where.

Ask for a show of hands: who only uses prints? Reassure them both tools have a place. Timing: ~4 min.

Sample Bug Pattern

Intended: sum integers 1 through 5 → expect 15. Actual output: 10.

total = 0
for i in range(1, 5):   # intended: sum 1..5
    total += i
print(total)  # prints 10, expected 15 — range stops early

Demo angle

Breakpoint inside the loop; watch i and total each step until learners spot that range(1, 5) never yields 5.

Don’t spoil the fix yet — let the simulator reveal it. Remind: Python range is exclusive at the end. Timing: ~3 min.

Demo Sequence

  1. Open the prepared Python sample with a known bug (wrong total / off-by-one loop)
  2. Set a breakpoint on the first suspect line (red dot in the gutter)
  3. Start Debugging (F5) — program pauses at the breakpoint
  4. Inspect Locals / Watch — note unexpected values
  5. Step Over line-by-line until the value goes wrong; fix the logic
  6. Remove the breakpoint, re-run, and confirm the expected output

Fix for our sample: change range(1, 5) → range(1, 6) (or range(1, 5 + 1)) so i reaches 5.

Project your IDE and follow the six steps live if time allows. Keep the sample under ~40 lines. Timing: ~7 min.
Case study

Case Study: Jordan’s Marks App

Belfast FE college · Level 2 Programming 45-minute practical Python + VS Code

Jordan built a short script to average five coursework marks. The tutor brief says the average of 10, 20, 30, 40, 50 must be 30. Jordan’s program printed 24. Panic prints of every line made the console unreadable.

With the tutor, Jordan set a breakpoint on the loop that adds marks, watched total and the loop index, and spotted an off-by-one: the loop used range(len(marks) - 1), skipping the last mark. One-line fix, re-run, average = 30. Evidence: screenshot of Watch before/after plus the fixed file.

Symptom

Average too low — last value never added

Debugger move

Breakpoint in loop + Watch on total & index

Fix

Loop over all indexes; confirm expected output

Named scenario for portfolio language. Ask: “What would print-debugging have looked like here?” Timing: ~5 min.

Common Debugger Faults

SymptomLikely causeFix
F5 does nothing / no pause No breakpoint set, or wrong file launched Click gutter for a red dot; check launch config / open the .py file
Steps into library forever Used Step Into on a built-in call Use Step Over (F10); Step Into only for your own functions
Watch shows “not available” Variable out of scope / not created yet Step until the assignment runs; watch names that exist in Locals
Bug vanishes when debugging Timing / race, or different input data Reproduce with the same inputs; log timestamps if concurrent
Output still wrong after “fix” Old process still running / didn’t save Stop debugger, save file, clear breakpoints, Run without debugging once

Practical Task

Brief: Open the prepared buggy sum script (or recreate the sample). Use the debugger — not print statements — to find why the total is 10 instead of 15. Fix the range, re-run, and collect evidence.

Success criteria

  • Breakpoint set on a sensible line (loop or total update)
  • Can Step Over and explain what changes in Watch
  • Identifies that range(1, 5) excludes 5
  • Fix applied; program prints 15
  • Breakpoints cleared; clean re-run confirmed

Evidence checklist

  • Screenshot: paused at breakpoint with Locals/Watch
  • Screenshot or note: i and total mid-loop
  • Corrected source file committed or submitted
  • One sentence: why debugger beat print here

Jargon Buster

Debugger
Tool that runs your program under control so you can pause, inspect, and step.
Breakpoint
A marker that pauses execution just before that line runs.
Step Over
Execute the current line (including a whole call) without entering the function body.
Step Into
Enter the function call on the current line to debug inside it.
Step Out
Run until the current function returns, then pause in the caller.
Continue
Resume running until the next breakpoint or the program ends.
Watch
Pane where you pin variables/expressions to see them update each step.
Locals
Automatic list of variables in the current function/scope.
Call Stack
List of active function frames — who called whom to reach this line.
Off-by-one error
Logic fault where a loop or index is short/long by one (classic with range).
Print-debugging
Inserting print/log statements to infer state — useful but messy at scale.
Gutter
The left margin of the editor where line numbers and breakpoint dots appear.
Launch configuration
JSON settings telling the IDE how to start your program under the debugger.
Exception breakpoint
Pause automatically when an exception is thrown, even without a line breakpoint.
