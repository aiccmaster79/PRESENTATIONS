Why This Matters

A Friday push to unprotected main can ship a broken donate form. No tests run. The charity site collects nothing all weekend. CI would have turned that push red before anyone merged.

PushSend commits to GitHub
CISame checks every time
PRReview before merge

Consequence

“Works on my PC” is not a release strategy. Automated checks plus a protected main branch stop one tired Friday from becoming a Monday incident.

Hook with the weekend-outage story. Ask who has merged without looking at checks. Timing: ~4 min.

Git vs GitHub

Git (local)

  • Version control on your machine
  • Init, add, commit, log
  • History lives in the hidden .git folder
  • Covered in deck #56

GitHub (remote)

  • Hosted copy of the repository
  • Issues, pull requests, reviews
  • Teams share one source of truth
  • Actions run checks in the cloud
Stress Git ≠ GitHub. GitHub is one remote host; GitLab and Bitbucket exist too. Timing: ~4 min.

CI vs CD

Continuous Integration

  • Automatically build and test each change
  • Runs on push and on pull requests
  • Catch bugs before they reach users
  • Today’s classroom focus

Continuous Delivery / Deploy

  • Release only when checks are green
  • Same steps every time — no “copy the files”
  • Can publish a site or package automatically
  • Next step once CI is trusted
Keep CD as a teaser. Learners should leave able to define both in one sentence. Timing: ~4 min.

The Delivery Pipeline

1. Code

Commit locally with Git

2. Push

Send to the GitHub remote

3. CI runs

Actions tests, lint, or build

4. CD (optional)

Deploy only if green

Classroom focus

Prove the CI loop: push → workflow runs → see pass or fail. CD waits until checks are trusted.

Minimal Workflow Shape

name: CI
on: [push, pull_request]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Run checks
        run: |
          echo "Hello from CI"
          # npm test / python -m pytest / ...

Teacher tip

File lives at .github/workflows/ci.yml. Keep the first job tiny and visible. Learners should see the YAML, the push, and the Actions log in one demo pass.

Leave this up as a cheat sheet during the lab. Indentation in YAML matters. Timing: ~5 min.

Case study

Knight Capital, 2012

New York · August 2012 Bad deploy, no automated gate ~$440 million in 45 minutes

Knight Capital deployed trading software with an old unused flag still live. There was no automated check to stop the release. In 45 minutes the firm lost about $440 million and had to be rescued. A protected branch plus a failing status check would not have saved every bug — but it would have forced a human gate before production.

Classroom parallel

The donate-form site is the same idea at student scale: never merge to main while the check is red. Always require a green CI run before merge.

Keep the finance detail light. The lesson is the missing gate, not stock trading. Timing: ~5 min.

Practical Task: Green, then Red

Brief

  • Create or clone a small GitHub repository
  • Add .github/workflows/ci.yml
  • Push and open the Actions tab
  • Break a check on purpose, then fix it
  • Open a pull request that shows the status

Success criteria

  • YAML is in the correct folder
  • You can point to a green run and a red run
  • You can name the failing step from the log
  • The PR shows the status check
  • No secrets appear in the file

Evidence checklist

  • Screenshot of a green Actions run
  • Screenshot of a red Actions run (or a failing PR check)
  • The ci.yml you used
Circulate and fix YAML indent / wrong folders early. Collect screenshots for portfolios. Timing: ~15–20 min.

Jargon Buster

Remote
A hosted copy of the repository (often named origin) that the team shares.
Pull request (PR)
A proposed change on a branch, opened for review before it is merged.
Review
A teammate’s verdict on a PR: comment, approve, or request changes.
Merge
Bring the PR branch into the target branch (usually main).
CI
Continuous Integration — automatically build and test every change.
CD
Continuous Delivery or Deploy — release automatically once checks are green.
Workflow
A YAML file that tells GitHub Actions when to run and which jobs to perform.
Job
A set of steps that run together on one runner (e.g. build on ubuntu-latest).
Step
One action inside a job: checkout the code, then run a command.
Runner
The machine that executes the job — usually a hosted ubuntu-latest VM.
YAML
The indented text format used for workflow files. Spaces matter.
Status check
The pass/fail result a workflow reports back onto a commit or PR.
Branch protection
Rules that block direct pushes and require PRs, checks, or reviews.
Secret
A token stored in repo settings and injected at run time — never committed.
Actions tab
The GitHub page that lists workflow runs and their logs.
Give two minutes to search three terms, then ask someone to use status check in a sentence. Timing: ~3 min.
