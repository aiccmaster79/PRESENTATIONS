Why Emulator Setup Matters

An Android emulator is a virtual Android device that runs on your computer. It lets testers install builds, check layouts, read Logcat, and repeat tests without needing a drawer full of phones.

AVDAndroid Virtual Device
APIAndroid platform version
LogcatEvidence for faults

Key idea

Use an emulator for repeatable classroom testing, but use a real phone for sensors, battery, camera quality, Bluetooth, and real performance checks.

Contrast emulator convenience with physical-device realism. Ask learners for examples where real hardware matters. Timing: about 4 minutes.

The Android operating system package the emulator boots. It must be downloaded before launch.

Cold boot

Logcat

Android's live log. Testers capture error messages, app crashes, and useful evidence here.

Virtualisation

CPU support such as Intel VT-x or AMD-V. Without it, the emulator may crawl or fail to start.

Emulator vs Real Device

Emulator strengths

  • Repeat the same setup across a lab
  • Switch API versions and screen sizes quickly
  • Reset, snapshot, and cold boot without damaging hardware
  • Capture screenshots and Logcat evidence on the PC

Real device strengths

  • Real camera, GPS, Bluetooth, sensors, and battery behaviour
  • True performance on low-end hardware
  • Manufacturer customisations and accessibility settings
  • User handling: glare, fingers, rotation, and network movement
Make the trade-off explicit. Explain that good testers know which environment gives trustworthy evidence. Timing: about 4 minutes.

The Setup Flow

1. Open tools

Start Android Studio, open Device Manager, and check SDK Manager if images are missing.

2. Pick profile

Choose a common phone such as Pixel 4a or Pixel 6 for classroom testing.

3. Choose image

Select a sensible API level, download it early, and avoid multiple huge images.

4. Launch and test

Cold boot if needed, install the demo app, run it, and collect screenshot plus Logcat evidence.

Rule of thumb: choose a stable API used by your course demo, not the newest image just because it exists.

Walk the class through Device Manager terminology before opening Android Studio. Timing: about 4 minutes.

Demo Sequence: First Launch

  1. Android Studio: open More Actions > Virtual Device Manager.
  2. Create device: choose a phone profile and click Next.
  3. System image: choose the agreed API level; download if required.
  4. Advanced settings: check RAM, graphics, storage, and startup orientation.
  5. Run: press Play, wait for home screen, then install or run the demo app.

Case Study: Belfast FE Lab

Belfast FE labFirst lesson delayImages + virtualisation

A mobile apps class planned a first emulator lesson. The tutor assumed every PC was ready. On the day, half the machines had virtualisation disabled and none had the system image downloaded. A 20 minute demo became a full-period setup rescue.

What went wrong?

System images were several GB, download throttling slowed the lab, and BIOS settings required technician access.

What changed?

The team created a pre-flight checklist: VT-x/AMD-V on, one API image downloaded, 20 GB free disk, and one known-good AVD tested.

Ask learners which checks could be done before the class arrived. Connect the story to professional lab readiness. Timing: about 5 minutes.

Practical Task: Build and Prove an AVD

Brief: Create an AVD, cold boot it, install or run the demo app, then collect evidence that proves the emulator is ready for app testing.

Success criteria

  • AVD uses agreed phone profile and API level
  • Emulator reaches Android home screen after cold boot
  • Demo app installs or runs without crashing
  • Logcat is visible and filtered to the app or error level

Evidence

  • Screenshot of AVD configuration/details
  • Screenshot of Android home after cold boot
  • Screenshot of demo app running
  • Short Logcat export or screenshot showing app start
Set a time box and require file names. Remind learners not to submit only a screenshot of Android Studio. Timing: about 12 minutes.

Searchable Glossary

AVD
Android Virtual Device: saved emulator hardware and software profile.
System image
The Android OS package the emulator boots from.
API level
Number identifying an Android platform version and available features.
Device Manager
Android Studio screen for creating, editing, and launching AVDs.
Cold boot
Start the virtual device from a clean powered-off state.
Quick Boot
Restore the emulator from a saved state for faster startup.
Logcat
Android logging view used to diagnose crashes and app behaviour.
Virtualisation
CPU feature that accelerates virtual machines and emulators.
RAM
Memory allocated to the emulator; too little can cause crashes.
Graphics mode
Hardware, software, or automatic rendering for the emulator display.
SDK Manager
Android Studio tool for installing platform packages and images.
Snapshot
Saved emulator state that speeds up future starts.
ADB
Android Debug Bridge, used to install apps and talk to devices.
Real device
A physical phone or tablet used when hardware behaviour matters.

Key Takeaways

Emulators are repeatable

Resources matter

Evidence matters
