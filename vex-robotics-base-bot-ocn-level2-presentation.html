Glossary

V5 BrainMain controller that runs the program and drives motors and sensors.
Base BotStarter VEX drivetrain platform used to learn build and control fundamentals.
Smart MotorV5 motor with built-in encoder feedback for speed and position control.
Encoder / rotation sensorCounts how far a motor or wheel has turned so distance can be measured.
Distance sensorMeasures how far objects are — often ultrasonic on classroom kits.
IMUInertial Measurement Unit — tracks heading and motion for straighter drives.
Differential steeringTurning by running left and right drive sides at different speeds.
Gear ratioTrade-off between wheel speed and pushing torque.
AutonomousRobot follows pre-written code with no live driver input.
Driver controlStudent operates the robot live with a controller during a match.
VEXcodeOfficial IDE with Blocks and text (C++) programming for VEX robots.
ChassisStructural frame that holds motors, brain, battery and wheels.

Hook

4 minutes · slide 2 of 18

Hold up a motor cable. Ask who owns the fault when a “working” program fails.

A working program still fails

If a drive motor cable is half-seated, the Base Bot pulls left, burns a port, or tips a scoring object — and the class blames the code.

Getting the build wrong wastes match time. Getting the responsibility wrong wastes learning time.

Say: “Hardware and code fail as a team — diagnose both.”

Timing: 4 minutes. Use a real loose cable demo if safe. Consequence must feel concrete before objectives.

The left side of the Base Bot barely moves. The program spins both motor groups at 50%. Hands up — where do you look first?

Start at the left motor cable and port. A half-seated smart-motor cable or a seized wheel makes “identical” code drive unevenly — rewriting the loop hides the real fault.

Chapter 04

Code

5 minutes · slide 9 of 18

Type or project this live in VEXcode if the projector allows.

Worked example

Drive both sides forward at half power. Same command · same expectation · then measure with encoders later.

// VEXcode text sketch — drive forward
MotorGroup Drive = MotorGroup(LeftMotors, RightMotors);
Drive.spin(forward, 50, percent);

Blocks path: Drivetrain → drive forward · set velocity 50%.

Timing: 5 minutes. Contrast Blocks vs text without ranking them — both are VEXcode.

Chapter 04

Code

5 minutes · slide 10 of 18

Every build choice is a trade. Force learners to name what they give up.

Trade-offs

Speed vs torque

Gear for push power and you lose top speed on long runs.

Blocks vs C++

Blocks teach flow fast; text scales for teams and reuse.

Auto vs driver

Autonomous needs sensors and testing; driver control needs practice under pressure.

Weight vs stability

Center the brain and battery — high mass tips scoring objects and curves drives.

Timing: 5 minutes. Ask pairs to pick one trade-off for their next build decision.

Activity · diagnose

Autonomous: drive 100 cm forward. The bot stops at ~60 cm every run. Battery is full. Distance sensor faces the floor. What failed?

The distance sensor is reading the floor, so the stop condition fires early. Remount it level to the field — otherwise every “tune the motors” change hides a sensing fault and costs match points.

Timing: 7 minutes. Reward evidence language: what the sensor sees, not vibes.

Chapter 05

Practice

4 minutes · slide 12 of 18

Named classroom story — keep it local and believable.

Case · Friday skills match

Team North built a Base Bot for a 60-second skills run: 15 s autonomous, then driver control.

Autonomous scored zero. Driver control looked fine. The team rewrote drive code three times before anyone checked the Brain — the autonomous program slot was empty.

Consequence: practice time burned on the wrong layer of the stack.

Timing: 4 minutes. Ask which checklist item would have caught this in one minute.
