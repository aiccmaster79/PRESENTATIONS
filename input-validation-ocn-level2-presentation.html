Why Validation Matters

Users type unexpected values — blanks, letters in number fields, ages of 999. Input validation checks data before the program uses it, so you avoid crashes, corrupt records, and confusing results. In industry, validation is the first line of defence for forms, APIs and file imports.

Three Input Types

Normal & Extreme

  • Normal — typical valid values (age 25)
  • Extreme / boundary — edges of allowed range (age 0 or 120)
  • Should be accepted if within rules
  • Boundaries catch off-by-one mistakes

Erroneous

  • Wrong type ("twenty" for age)
  • Out of range (−5, 999)
  • Empty / blank when required
  • Should be rejected with a clear message
Ask for one normal, one extreme, one erroneous example for a score 0–100. Timing: ~5 min.
Toolkit

Validation Types

Click or press Enter/Space to flip each card

Presence

Is the field filled? Reject blank or whitespace-only input when a value is required.

Type

Is it the right kind of data? Whole number vs text vs yes/no — check before comparing ranges.

Range

Is the value between allowed limits? Age 0–120, score 0–100 — include extremes if the brief says so.

Format

Does the pattern match? Email with @, date DD/MM/YYYY, postcode shape — not just “any text”.

Length

Too short or too long? Passwords often need a minimum; names may have a maximum.

Whitelist

Is the value in an allowed set? e.g. title must be Mr/Ms/Mx — reject anything else.

Pairs flip and teach one type each. Stress: check type before range. Timing: ~6 min.

Validation Sketch

raw = input("Age (0-120): ").strip()
if not raw:                          # presence
    print("Age is required.")
elif not raw.isdigit():              # type
    print("Please enter a whole number.")
else:
    age = int(raw)
    if age < 0 or age > 120:         # range
        print("Age must be between 0 and 120.")
    else:
        print(f"Saved age: {age}")

Order matters: presence → type → range (or format). Comparing letters as numbers is a classic crash.

Walk the three checks. Don’t spoil every message — learners edit messages in the sandbox next. Timing: ~4 min.

Demo Sequence

  1. Introduce a tiny program that asks for age or a score (0–100)
  2. Show a test plan table: Normal / Extreme / Erroneous with expected results
  3. Run normal values — success path
  4. Run boundaries (0 and 100 / 120) — should pass if inclusive
  5. Run erroneous values (letters, blank, 999) — show friendly errors
  6. Improve the message text with the class, then re-test

Mini plan: 25 → Accept · 0 / 120 → Accept · abc / "" → Reject · 999 → Reject (out of range)

Case Study: Aoife’s Signup Form

Belfast FE college · Level 2 Programming 45-minute practical Python console form

Aoife built a club signup script: name, age (13–19), and email. Testers entered abc for age and the program crashed with a ValueError. Blank emails were saved as empty strings. The tutor asked for a test plan covering normal, extreme and erroneous cases.

Aoife added presence and type checks before int(), range checks for 13–19, and a simple @ check for email. She rewrote messages (“Please enter a whole number between 13 and 19”) and recorded a table of six tests with Pass/Fail. Evidence: test plan photo plus the validated script.

Common Validation Faults

SymptomLikely causeFix
Crash on letters / ValueError Converted with int() before type check Check isdigit() / try-except before converting
Boundary rejected (0 or 100) Used < / > instead of inclusive limits Match the brief: usually >= min and <= max
Blank accepted as valid No presence check; only range checked strip() then reject empty string
Cryptic error / stack trace Exception printed raw to the user Catch errors; print a friendly, specific message
Tests miss real bugs Only tried “happy path” normals Plan Normal + Extreme + Erroneous before coding

Practical Task

Brief: Write (or extend) a small program that validates age 0–120. Build a six-row test plan covering Normal, Extreme and Erroneous. Run each test, record Pass/Fail, and improve at least one user message based on feedback.

Success criteria

  • Presence, type and range checks in sensible order
  • Boundaries 0 and 120 accepted if the brief allows
  • Letters, blank and out-of-range rejected
  • Friendly, specific fail messages (no stack traces)
  • Test plan table completed with expected vs actual

Evidence checklist

  • Photo or file of the completed test plan
  • Screenshot: normal success path
  • Screenshot: erroneous rejection + message
  • Source file with validation checks
Circulate and coach message wording. Collect test plans for portfolios. Timing: ~15–20 min.

Jargon Buster

Input validation
Checking user data against rules before the program uses or stores it.
Normal input
A typical valid value inside the allowed rules (e.g. age 25).
Extreme / boundary
A value at the edge of an allowed range (e.g. 0 or 120) that should still pass if inclusive.
Erroneous input
Invalid data — wrong type, out of range, blank, or bad format — that should be rejected.
Presence check
Ensuring a required field is not blank after stripping whitespace.
Type check
Confirming the data is the right kind (number, text, boolean) before further checks.
Range check
Ensuring a numeric value lies between minimum and maximum limits.
Format check
Ensuring a value matches an expected pattern (email, date, postcode).
Test plan
A table of inputs, classifications, expected results and actual outcomes used to prove validation works.
Whitelist
An allowed set of values; anything not in the list is rejected.
Sanitise
Cleaning input (e.g. strip spaces) before or alongside validation.
User message
Clear text telling the user what went wrong and how to fix the input.
Off-by-one (validation)
Rejecting a valid boundary because the comparison used the wrong operator.
Never trust input
Principle that all external data may be wrong or hostile — validate before use.
