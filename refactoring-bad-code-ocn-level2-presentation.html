Refactoring Bad Code

Improve code without changing what it does

OCN NI Level 2–3 — Programming
Welcome the group. Frame the lesson as “same results, cleaner insides”. Mention messy sample + output checklist for the practical. Timing: ~2 min.

Learning Objectives

By the end of this session, you will be able to:

  • Define refactoring vs rewriting features
  • Spot common “code smells” (duplication, bad names, long functions)
  • Improve a messy sample while keeping the same outputs
  • Use tests or fixed example inputs to prove behaviour is unchanged
  • Explain why readable code matters for teams
Read objectives aloud. Ask who has rewritten a working script “just to tidy it” — introduce the safety-net idea early. Timing: ~3 min.

Why Readable Code Matters

Refactoring is how teams keep software alive. Messy code that “works” still costs time: every change risks a bug, every new teammate needs a longer briefing, and every deadline becomes a scramble.

Classroom tip

Capture current outputs first (or keep a tiny test). Refactor in small steps; re-check after each change.

Hook: “Would you rather inherit 40 clear lines or 40 mysterious ones?” Stress that refactoring is professional practice, not fussy perfectionism. Timing: ~4 min.

Refactor ≠ New Features

Feature work

  • Adds or changes what the program does
  • New buttons, rules, screens, outputs
  • Needs fresh tests for new behaviour
  • User-visible change is the goal

Refactoring

  • Improves structure, names, clarity
  • Same inputs → same outputs
  • Uses existing checks as a safety net
  • Internal quality is the goal
Resist the urge to “just add one more thing” mid-refactor. Behaviour freeze is the teaching point. Timing: ~4 min.

Safe Refactor Sequence

  1. Run the “bad” sample; record outputs for fixed inputs
  2. Identify smells with the class (names, duplication, magic numbers)
  3. Rename variables/functions for clarity
  4. Extract a function or constant; remove duplication
  5. Re-run the same inputs — outputs must match
  6. Optional: add a tiny assert/test that locks behaviour
Project this during the live demo. One smell per commit if using Git. Timing: ~5 min.

Red flag

If outputs change, you did not only refactor — you changed behaviour. Undo and separate the feature from the tidy-up.

Case Study: School Shop Till

Campus café Python till script 45-minute practical

Scenario: The student shop’s discount script works — c(120) prints 108.0 — but three volunteers maintain it and nobody knows what c means. A magic 0.9 appears in four places. A new volunteer almost “fixed” it by changing the rate while renaming variables.

Approach: Freeze outputs on a checklist → rename → extract DISCOUNT_RATE once → re-run. Feature request (student loyalty 15%) waits for a separate change after the tidy-up.

Named scenario for portfolio language. Ask: “What would have happened if they mixed the rate change with the rename?” Timing: ~5 min.

Success criteria

  • Output checklist completed before edits
  • At least one rename for clarity
  • At least one named constant or extract
  • Same inputs produce same outputs
  • Two-sentence reflection written

Evidence checklist

  • Screenshot of pre-refactor outputs
  • Screenshot of cleaned code
  • Screenshot of matching post-refactor outputs
  • Optional: tiny assert run green

Jargon Buster

Refactoring
Improving code structure and clarity without changing external behaviour.
Code smell
A surface clue that design may be weak — e.g. duplication or bad names.
Magic number
An unexplained literal value in code; better as a named constant.
Duplication
The same logic repeated; extract once and reuse (DRY).
Extract function
Move a chunk of code into a named function for reuse and clarity.
Rename
Change a variable/function name so intent is obvious.
Behaviour preservation
Same inputs still produce the same outputs after a change.
Safety net
Fixed examples or automated tests that prove behaviour stayed put.
Mixed concerns
Input, calculation, and output tangled in one block — hard to test.
Long function
One oversized block doing too many jobs; split it up.
Named constant
A clear identifier for a fixed value (e.g. DISCOUNT_RATE).
Technical debt
Shortcuts that save time now but cost more later to maintain.
Assert
A check that fails loudly if a condition is false — locks expected results.
DRY
“Don’t Repeat Yourself” — prefer one clear definition over copy-paste.
