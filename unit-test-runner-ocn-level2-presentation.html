Why Unit Test Runners Matter

Manual checking is useful, but it is easy to forget a case. A unit test runner executes a repeatable list of tiny checks and reports exactly which behaviour passed or failed.

SecondsFast feedback while coding
NamedFailures point to one behaviour
RepeatableSame checks every run

Testing habit

Do not just ask "does the program start?" Ask "which small behaviours have evidence that they still work?"

Timing: 4 minutes. Contrast a quick manual run with automated checks that can be repeated after every code change.
Core concept

What a Unit Test Checks

Small unit

A function, method, class, or module behaviour that can be checked in isolation.

Known input

The test provides a clear input or setup, such as add(2, 3).

Expected output

An assertion compares the actual result with what should happen.

test("adds two numbers", () => {
  expect(add(2, 3)).toBe(5);
});
Timing: 5 minutes. Point to the three parts: named behaviour, action, assertion. Avoid tool-specific detail beyond the simple example.
Interactive vocabulary

Flip Cards: Test Types and Structure

Click or press Enter/Space to flip each card.

Unit test

Checks one small behaviour, usually without real databases, networks, or full user journeys.

Integration test

Checks that several parts work together, such as code plus a database or API wrapper.

System test

Checks a larger end-to-end workflow, closer to how a user experiences the system.

Arrange

Prepare data, inputs, fixtures, or mocks needed for the behaviour under test.

Act

Call the function or method being tested.

Assert

Check the actual result against the expected result, and fail clearly if they differ.

Timing: 6 minutes. Let pairs flip cards, then ask them to sort examples into unit, integration, and system testing.

How to Read a Failure

Test name

The name should describe behaviour: "applies ten percent discount".

Expected vs actual

Expected is what the test wanted; actual is what the code returned.

File and line

The stack trace points to the assertion and sometimes the function under test.

Expected: 90
Received: 100
at cart.test.js:12:28
Timing: 5 minutes. Reinforce that the failure points to a clue, not always the exact bug. The code or the test might be wrong.

Assertions: Tiny Claims About Behaviour

An assertion is a statement the test runner can check. If the statement is false, the test fails and prints evidence.

expect(add(2, 3)).toBe(5);
expect(validateEmail("sam@example.com")).toBe(true);
expect(cart.items).toHaveLength(2);

Good assertion

Specific enough to catch a bug, but focused on behaviour rather than hidden implementation detail.

Timing: 5 minutes. Explain that assertions are not guesses; they encode the behaviour we expect from requirements or examples.

Worked Example: Discount Function

Test

test("applies 10% discount", () => {
  expect(calculateDiscount(100, 10)).toBe(90);
});

Buggy code

function calculateDiscount(price, percent) {
  return price;
}

The runner says Expected: 90 and Received: 100. That evidence tells us the function ignored the discount.

Timing: 5 minutes. Talk through the example line by line and link it to the terminal failure from the interactive.

Case Study: The "Fixed" Classroom Function

Classroom scenario Silent failure No test run

A learner "fixed" a validateEmail() function by checking for an @ symbol. Their demo email passed, so they submitted the work without running the test suite.

The hidden tests included "sam@", "@example.com", and an empty string. The function returned true for two invalid addresses, so the form quietly accepted bad data.

Lesson: a manual demo can show one happy path. A unit test suite gives evidence across normal, extreme, and erroneous inputs.

Timing: 6 minutes. Invite learners to list the test inputs that would have caught the silent failure before submission.

Common Unit Testing Faults

Symptom Likely cause Fix
False green: tests pass but app still broken Tests missed the risky case or asserted the wrong behaviour Add examples from requirements, bug reports, and edge cases
Brittle asserts fail after harmless refactor Test checks exact formatting, order, or internal detail unnecessarily Assert the behaviour the user or caller depends on
Testing implementation, not behaviour Test knows private variables or step-by-step algorithm choices Prefer public inputs and outputs; keep internals flexible
Only happy-path tests Normal examples were tested, but invalid or boundary input was skipped Use normal, extreme, and erroneous cases
Slow tests ignored by developers Unit tests depend on real services or long setup Use fixtures, mocks, and a separate integration test layer
Timing: 8 minutes. Emphasise the three required faults: false green, brittle asserts, and testing implementation rather than behaviour.

Choosing Useful Test Cases

For validateEmail()

  • Normal: sam@example.com
  • Missing domain: sam@
  • Missing name: @example.com
  • Empty: ""
  • Spaces: "sam example.com"

Good names

  • rejects empty email
  • rejects missing domain
  • accepts simple valid address
  • trims surrounding spaces
  • reports helpful error message

What Unit Tests Do Not Prove

Usability

A function can pass tests while the interface confuses users.

Integration

A unit can work alone but fail when the database, API, or file system is involved.

Performance

Fast unit tests do not prove the full system handles load or stress.

Unit tests are a foundation. They work best alongside regression, usability, integration, and load testing.

Practical Task: Run, Read, Improve

Brief

  • Open a small function and its unit tests
  • Run the test suite
  • Record pass/fail summary
  • Fix one failing behaviour
  • Run the suite again

Success criteria

  • You can name the failed test
  • You can state expected and actual values
  • Your fix targets behaviour, not random output
  • All relevant tests pass after the fix
  • You explain one limitation of the unit tests
Timing: 7 minutes. Set up the practical and make sure learners know evidence matters as much as the final green result.

Evidence Checklist

  • Screenshot or copied text of the first failed test output
  • Short note: test name, expected value, actual value
  • Code snippet showing the changed function or assertion
  • Screenshot or copied text of the passing test run
  • One sentence explaining why the new result is more trustworthy than a manual demo only
EvidenceWhat it proves
Before outputYou could read and diagnose a failure.
Changed codeYou made a focused behaviour fix.
After outputThe automated checks now pass.
Timing: 4 minutes. Explain that evidence prevents "it works on my machine" claims and supports assessment decisions.

Jargon Buster

Unit test
A small automated check for one function, method, class, or module behaviour.
Test runner
A tool that discovers tests, executes them, and reports pass/fail output.
Assertion
A check that compares actual behaviour with expected behaviour.
Fixture
Reusable setup data or objects used by tests.
Mock
A controlled fake object or function used to isolate the unit under test.
Coverage
A measure of which code lines or branches were executed by tests.
Red-green-refactor
Write a failing test, make it pass, then improve the code while tests stay green.
Regression
A bug that comes back or a feature that breaks after a change.
Test suite
A collection of tests run together.
Skipped test
A test the runner intentionally does not execute, usually marked pending or disabled.
False green
A passing result that gives false confidence because the tests did not check the important case.
Brittle assert
A fragile check that fails after harmless internal changes.
Arrange, Act, Assert
A common structure: set up inputs, call the behaviour, then check the result.
Stack trace
Diagnostic output showing where a failure or error happened.
