Good Bug Report

Turn a discovered fault into a clear, reproducible, useful ticket.

OCN NI Level 2/3 Software Testing

  • Distinguish severity from priority and avoid mixing multiple bugs into one ticket.

The Anatomy of a Useful Report

Title

Specific symptom and area.

Steps

Ordered actions from a known state.

Expected/Actual

The gap that proves the fault.

Environment

Device, browser, build, data.

Evidence

Screenshot, video, logs, IDs.

Severity: Major
Environment: Android 14, Chrome 126, staging build 2.8.4

Expected: Voucher rejected with message

Reproducibility Is the Core

Weak report

  • Starts from the middle of the story
  • Uses vague language like "broken"
  • Hides test data and account details
  • Leaves the developer guessing

Reproducible report

  • Begins from a clean, known state
  • Lists actions in the order taken
  • Names exact data, build, device, and user role
  • Shows expected and actual outcomes
Delivery cue: ask learners to identify what a developer can do with the right-hand report that they cannot do with the left. Timing: 4 minutes.

Severity, Priority, and One Bug Per Ticket

Severity

How bad is the impact? Data loss, crash, security issue, incorrect result, or cosmetic problem?

Priority

How soon should it be fixed? This includes deadlines, users affected, business value, and release risk.

One bug per ticket

Separate faults can have separate causes, owners, tests, fixes, and release decisions.

Example

A typo on the homepage may be low severity but high priority before a public launch. A rare admin crash may be high severity but lower priority if only internal staff can trigger it.

Delivery cue: invite learners to classify a few examples before showing the explanation. Timing: 4 minutes.

Steps

Gives a numbered route from a known start to the fault, using exact data and actions.

Expected / Actual

Separates what should happen from what did happen so the defect is measurable.

Environment

Records build, browser, OS, device, network, role, and test data that might affect reproduction.

Evidence

Adds screenshots, videos, logs, timestamps, console errors, and request IDs to shorten diagnosis.

Severity

States the user or system impact without deciding the whole release schedule on its own.

Bad vs Good Compare

Login broken

It does not work. I tried logging in and got an error. Please fix ASAP.

Missing repro route

No role, URL, account state, browser, or exact action sequence.

No expected result

The developer cannot tell whether the issue is validation, authentication, or display.

No evidence

"Error" is not enough; include the message, screenshot, logs, and timestamp.

Compare how much guesswork each ticket creates.

A Reliable Repro Workflow

Start clean

Use a known account, reset data, clear filters, and record the build.

Isolate

Remove unrelated actions until the smallest repeatable path remains.

Repeat

Run the steps twice. If it happens sometimes, record the frequency.

Cross-check

Ask another tester to follow your steps before the ticket reaches development.

Delivery cue: frame this as scientific method for testers: setup, action, observation, repeat. Timing: 4 minutes.

Evidence and Environment Details

Strong evidence

  • Screenshot with the full page or error visible
  • Short video for timing, animation, or multi-step issues
  • Console error, network request ID, or server log reference
  • Timestamp, test account, data record, and build number

Environment clues

  • OS and version: Windows 11, Android 14, iOS 18
  • Browser and version: Chrome 126, Edge 126, Safari 18
  • App build, branch, API environment, feature flag state
  • Network, role, permission level, locale, screen size
Delivery cue: point out that environment does not mean every device detail, only the details that could change the result. Timing: 4 minutes.

Classroom SaaS scenarioAuthenticationTriage delay
09:10 Mon

Support files a ticket: "Login broken for students" with no browser, school, screenshot, URL, or account role.

14:30 Mon

Developers cannot reproduce on staff accounts. They suspect a recent password reset change and start reading unrelated code.

11:45 Tue

A tester adds evidence: Safari on managed iPads, student role, school SSO, error after tapping "Continue" twice.

Extended Practical Task

Scenario brief

You discover that applying an expired voucher during checkout sometimes creates a blank payment panel. Your job is to create a bug report that another tester and developer can reproduce without asking follow-up questions.

Success criteria

  • Title identifies feature, action, and failure
  • Steps begin from a known state and are numbered
  • Expected and actual results are separate and testable
  • Environment includes build, browser/device, role, and data
  • Severity is justified by user impact

Evidence checklist

  • Screenshot of blank panel and voucher value
  • Console error or network request ID
  • Timestamp and test account used
  • Note whether it reproduces 1/1, 2/3, or intermittently
  • Link to related regression or requirement if known
Delivery cue: give learners 12-15 minutes to draft, then pair review against the checklist. Timing: 15 minutes.

Jargon Buster

Severity
How serious the bug's impact is for users, data, security, or system stability.
Priority
How soon the team should fix it, considering business timing and release risk.
Repro
Short for reproduce: the ability to trigger the same bug by following the same steps.
Expected result
The behaviour that should happen according to requirements, design, or normal operation.
Actual result
The behaviour actually observed during the test.
Regression
A feature that used to work but fails after a code, data, or configuration change.
Blocker
A bug so severe it prevents testing, release, or a critical user journey from continuing.
Triage
The team process of reviewing, clarifying, prioritising, assigning, or closing tickets.
Environment
The conditions where the test ran: device, OS, browser, app build, role, data, and flags.
Build
A packaged version of the software, often with a number or commit reference.
Log
A record of events or errors that helps diagnose what the software did internally.
Evidence
Material attached to prove and explain the fault, such as screenshots, videos, logs, or IDs.
Intermittent
A bug that appears only sometimes, often because of timing, data, network, or state.
Duplicate
A ticket that reports the same underlying bug as an existing ticket.
Delivery cue: ask learners to search for "priority", "blocker", and "intermittent" before the quiz. Timing: 4 minutes.

Key Takeaways

Reproducible

Another person can follow the same path and see the same fault.

Diagnosable

Environment, data, logs, and evidence point towards likely causes.

Prioritisable

Impact and urgency are clear enough for triage decisions.

Collaborative

The report respects the time of testers, developers, support, and users.
